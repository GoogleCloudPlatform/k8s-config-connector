### [2026-06-03] DiscoveryEngine mixed v1 and v1beta service types generation
- **Context**: Implementing direct types for DiscoveryEngineSampleQuerySet (Issue #8713).
- **Problem**: `SampleQuerySet` is defined under `google.cloud.discoveryengine.v1beta`, but all other discoveryengine resources in `apis/discoveryengine/v1alpha1` are under `google.cloud.discoveryengine.v1`. Sequential runs of `generate-types` overwrite `types.generated.go`, deleting the other service's types and breaking compilation.
- **Solution**: Updated `generate.sh` to rename `types.generated.go` to `v1_types.generated.go` and `v1beta_types.generated.go` during sequential generation runs. The `PruneTypes` linter and Go `deepcopy` generator correctly parse all `*.generated.go` files, allowing types from both services to coexist and compile flawlessly.
- **Impact**: Enables co-existence of types from multiple service API versions under the same KCC group version folder without generation conflicts.

### [2026-06-05] DiscoveryEngineConversation Type Generation and Mapper Limitation
- **Context**: Implementing initial KRM types and IdentityV2 for `DiscoveryEngineConversation`.
- **Problem**: When generating types, nested protobuf types under skipped messages (e.g. `SearchResponse.Summary` inside `SearchResponse` which has the suffix `Response` and is thus skipped in `generatemappercommand.go`) did not get their mapper functions generated. Additionally, when types are first generated, they are commented out in `types.generated.go` as unreachable until the manual spec/status structs reference them.
- **Solution**: We referenced the nested types like `ConversationMessage` and `Reply` directly inside `DiscoveryEngineConversationSpec` in `conversation_types.go` and reran type generation, which successfully made the generator detect their reachability and automatically uncomment them in `types.generated.go`. To avoid mapper-compilation failures on local tests without committing mapper files (as instructed), we discarded changes to `mapper.generated.go` since no controller is registered to use the mappers yet.
- **Impact**: When adding new resources, make sure to completely specify their spec and status structures with the target protobuf types in the handwritten types file *before* final type generation, so the `prune-types` tool correctly marks them as reachable.

### [2026-06-05] Handling Unreachable Nested Types in Greenfield Generation
- **Context**: Implementing direct types for `DiscoveryEngineControl` under Issue #9237.
- **Problem**: When a new resource is first added to `generate.sh`, its nested types (e.g., `Condition`, `Control_BoostAction`) are initially generated as "unreachable types" and commented out in `types.generated.go`.
- **Solution**: First define the Spec fields referencing these types in `<resource>_types.go` and run `./generate.sh` again. The generator automatically identifies them as reachable, uncomments them, and makes them available.
- **Impact**: This avoids the need to manually copy or define nested proto structs, keeping types.generated.go fully managed by the builder.

### [2026-07-06] Handling Missing Imports (apiextensionsv1) in Generated Types
- **Context**: Implementing initial KRM types and IdentityV2 for `DiscoveryEngineSession`.
- **Problem**: Running `generate.sh` generated nested types (like `Session_Turn` and `Session_TurnObservedState`) which use `apiextensionsv1.JSON` for fields like `structData` under `Query`. However, because `apiextensionsv1` was not imported anywhere in the `v1alpha1` package (and wasn't generated into `v1_types.generated.go`), this resulted in a compilation failure (`use of unimported package "apiextensionsv1"`), which also broke the subsequent `controller-gen` (deepcopy & CRD) generators.
- **Solution**: We added a custom `goimports` run on `apis/discoveryengine/v1alpha1/` inside `generate.sh` right after the sequential generation of both `v1` and `v1beta` types. This ensures `goimports` runs over the newly generated types files and automatically injects the missing `apiextensionsv1` (and any other package) imports before `controller-gen` is run, allowing the entire pipeline to compile and generate cleanly in a single script run.
- **Impact**: Resolves the "unimported package" issue for any future resources under the same group that may reference nested protobuf fields utilizing `apiextensionsv1.JSON`.

### [2026-08-07] UserStore only exists in v1beta, and postdates the pinned googleapis SHA
- **Context**: Implementing initial KRM types, IdentityV2, and generate.sh for `DiscoveryEngineUserStore` (Issue #12023). The issue text says the service is `google.cloud.discoveryengine.v1`, matching the pattern of most other resources in this group.
- **Problem**: `google/cloud/discoveryengine/v1/user_store.proto` and `user_store_service.proto` do not exist upstream — `UserStore`/`UserStoreService` are only defined under `google.cloud.discoveryengine.v1beta` (confirmed via the `googleapis/googleapis` proto tree and `discoveryengine_v1.yaml`'s API list, which has no `UserStoreService`, only `UserEventService`/`UserLicenseService`). Worse, `user_store.proto` doesn't exist yet even at the googleapis SHA currently pinned in `apis/git.versions` (`1765b559c4...`) — that SHA also predates `license_config.proto`, so the pre-existing `DiscoveryEngineLicenseConfig`/`ServingConfig`/`SampleQuery(Set)` block in `generate.sh` would *also* fail with `proto: not found` if re-run today. This is a latent, pre-existing repo issue unrelated to UserStore.
- **Solution**: Added `DiscoveryEngineUserStore:UserStore` in its own dedicated `generate-types` block sourced from `google.cloud.discoveryengine.v1beta`, using a newer googleapis SHA fetched just for this resource via `./generate-proto.sh "<newer SHA>" "${REPO_ROOT}/.build/googleapis-discoveryengine-userstore.pb"` and `--proto-source-path` — the same pattern already established in `apis/gkehub/generate.sh`, `apis/mapmanagement/generate.sh`, `apis/dataform/generate.sh`, etc. for resources whose protos postdate the default pin. Left the existing (already-broken) `DiscoveryEngineLicenseConfig`/etc. block untouched since fixing it is out of scope for this issue. Mapper generation for UserStore is deliberately skipped (marked `NOTYET`, same as `apis/gkehub/generate.sh` does for its SHA-overridden resource) since no controller consumes it yet and the default mapper's proto source doesn't include UserStore.
- **Impact**: Future agents adding a DiscoveryEngine resource should first check whether its proto actually exists at the pinned SHA (`git -C .build/third_party/googleapis show <SHA>:google/cloud/discoveryengine/<version>/<file>.proto`) before assuming `v1` vs `v1beta` placement from the issue text alone — issue text can be stale/wrong about which proto version defines a resource. If the pinned SHA lacks the proto, use the per-service SHA-override pattern rather than bumping the global `apis/git.versions` (which has previously been reverted to avoid unrelated breaking changes in firestore/sql, see `git log -- apis/git.versions`).

### [2026-08-07] Windows/Git-Bash toolchain workarounds while implementing DiscoveryEngineUserStore
- **Context**: Same as above, implementing `DiscoveryEngineUserStore` on a Windows machine using Git Bash (MSYS2).
- **Problem 1**: `dev/tools/controllerbuilder/generate-proto.sh` invokes `protoc` with ~2200-2600 individual `.proto` file paths as separate argv entries. MSYS2's `ARG_MAX` (`getconf ARG_MAX` = 32000 on this machine) is far smaller than the ~250KB+ combined argument length, so `protoc` fails with `Argument list too long`, even after installing `protoc` correctly via `winget` (`libprotoc 35.1`) and building `bin/controllerbuilder`.
- **Problem 2**: `dev/tasks/generate-crds` computes `REPO_ROOT` via `git rev-parse --show-toplevel`, which on this Windows checkout returns a drive-letter path like `D:/GitRepos/k8s-config-connector`. `controller-gen`'s marker-option parser splits on `:`, so `object:headerFile=D:/GitRepos/...` is misparsed (the `D` after `headerFile=` is treated as a bogus extra option), and `controller-gen` exits with a marker-parsing error.
- **Solution 1**: `protoc` supports reading arguments from a response file (`protoc @args.txt`). Built the file list into a response file (one argument per line: flags, `-I` dirs, all `.proto` paths, `-o` output path) and invoked `protoc "@${RSPFILE}"` directly, bypassing the OS argv limit entirely. This is a local workaround only — `generate-proto.sh` itself was not modified, since on Linux/macOS CI runners `ARG_MAX` is large enough that the script's normal direct-argv `protoc` invocation works fine.
- **Solution 2**: Ran `controller-gen` from `apis/` using a **relative** `headerFile=../hack/boilerplate.go.txt` path instead of the `${REPO_ROOT}`-derived absolute path, avoiding the `D:` colon entirely. Also had to scope `paths=` to `./discoveryengine/v1alpha1/...` (a bare `./discoveryengine/...` errors with "no Go files in .../apis/discoveryengine" because the parent dir itself has no `.go` files — controller-gen's path loader doesn't recurse the same way `go build ./...` does with a single-level glob here) rather than `./...`, to avoid an extremely long, slow whole-repo regeneration; verified this produced byte-identical (aside from CRLF/LF) output for the other 12 already-committed DiscoveryEngine CRDs before copying only the new `discoveryengineuserstores` CRD into `config/crds/resources/`.
- **Impact**: Neither workaround required changing any shared script; both are documented here so a future agent hitting the same Windows-only failures doesn't waste time assuming they're KCC bugs. `dev/tasks/generate-gvks` and `dev/tasks/generate-cnrm-cluster-roles` did *not* add UserStore (confirmed `LicenseConfig` etc. are likewise absent), since those are driven by controller/reconciler registration, not just type existence — expected, since UserStore has no direct controller yet.
