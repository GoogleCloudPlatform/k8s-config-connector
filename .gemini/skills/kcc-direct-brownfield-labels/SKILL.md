# KCC Direct Brownfield Labels Skill

This skill provides clear, deterministic instructions and canonical code snippets for standardizing label reconciliation across all brownfield direct controller migrations.

## Background & Problem Statement
In Config Connector, brownfield resources (migrated from Terraform or DCL) map GCP labels from Kubernetes `metadata.labels` rather than `spec.labels`. Because autogenerated mappers (`Spec_ToProto` and `Spec_FromProto`) only convert fields in `Spec`, the Proto `labels` field is left unpopulated (`nil`).

When implementing direct controllers, contributors and automated coding agents frequently make common mistakes:
1. **Empty API Payloads:** Forgetting to assign `desired.Labels = label.GCPLabels(u)` in `buildDesired`, which causes `Create` and `Update` API requests to send empty/nil label maps to GCP.
2. **Missing Diff in Update:** Using `common.CompareBrownfieldSpec` instead of `common.CompareBrownfieldSpecAndLabels`, causing label modifications to be skipped or `"labels"` to be omitted from `UpdateMask`.
3. **Deprecated Helpers:** Using deprecated helpers like `label.NewGCPLabelsFromK8sLabels` or manual map copying instead of the canonical `label.GCPLabels(u)`.
4. **Untested Fixtures:** Forgetting to add/modify `metadata.labels` in E2E `update.yaml` test fixtures, allowing broken label reconciliation logic to slip past CI.

---

#### 1. Identifying Authoritative Label Support & Target Proto Field
The agent must inspect the legacy configuration to identify if labels are supported and determine the exact target Proto field name:
- **Terraform:** Check `config/servicemappings/<service>.yaml` for `metadataMapping.labels: <field_name>` (e.g., `labels`, `user_labels`).
- **DCL:** Look up the resource in `pkg/dcl/metadata/metadata.go` to get its `DCLVersion`, then verify `x-dcl-labels: <field_name>` in its schema:
  - For GA: `third_party/github.com/GoogleCloudPlatform/declarative-resource-client-library/services/google/<service>/<resource>.yaml`
  - For Alpha/Beta: `third_party/github.com/GoogleCloudPlatform/declarative-resource-client-library/services/google/<service>/<alpha|beta>/<resource>.yaml`

## 2. Canonical Implementation Pattern

### Step 2.a: Constructing Desired Proto in `buildDesired`
Mandate that `buildDesired` is the single source of truth for constructing the desired Proto (`*pb.<Kind>`), populating `desired.Labels` via `label.GCPLabels(u)`:

```go
func (a *adapter) buildDesired(ctx context.Context, u *unstructured.Unstructured) (*pb.<Kind>, error) {
    // Note: NormalizeReferences should be done if there are reference fields.
    if err := common.NormalizeReferences(ctx, a.kube, a.desiredKRM, nil); err != nil {
        return nil, fmt.Errorf("normalizing references: %w", err)
    }

    mapCtx := &direct.MapContext{}
    desired := <Kind>Spec_ToProto(mapCtx, &a.desiredKRM.Spec)
    if mapCtx.Err() != nil {
        return nil, mapCtx.Err()
    }

    // Populate desired GCP labels for both Create and Update payloads
    desired.Labels = label.GCPLabels(u)

    return desired, nil
}
```

> **Note:** `buildDesired` serves as the centralized place for all desired state pre-handling before invoking GCP APIs. In addition to assigning `desired.Labels`, use `buildDesired` for other pre-processing tasks such as:
> - Normalizing object references (`common.NormalizeReferences`).
> - Canonicalizing value formats (e.g., standardizing string casing, project number vs ID resolution, or relative vs full URL paths).
> - Applying default parameters or computed fields required by the GCP API.

### Step 2.b: Using `buildDesired` in `Create()`
```go
func (a *adapter) Create(ctx context.Context, createOp *directbase.CreateOperation) error {
    u := createOp.GetUnstructured()
    desired, err := a.buildDesired(ctx, u)
    if err != nil {
        return err
    }

    req := &pb.Create<Kind>Request{
        Parent: a.id.ParentString(),
        <Kind>: desired, // contains desired.Labels
    }
    ...
}
```

### Step 2.c: Using `buildDesired` and `CompareBrownfieldSpecAndLabels` in `Update()`
```go
func (a *adapter) Update(ctx context.Context, updateOp *directbase.UpdateOperation) error {
    u := updateOp.GetUnstructured()

    // 1. Build desired with latest labels
    desired, err := a.buildDesired(ctx, u)
    if err != nil {
        return err
    }

    // 2. Diff Spec and metadata.labels together
    diff, updateMask, err := common.CompareBrownfieldSpecAndLabels(
        ctx,
        u,
        &a.desiredKRM.Spec,
        a.actual,
        "labels", // Target proto field name (e.g., "labels" or "user_labels")
        <Kind>Spec_FromProto,
        <Kind>Spec_ToProto,
        normalize,
    )
    if err != nil {
        return fmt.Errorf("comparing %s: %w", a.id.String(), err)
    }

    // 3. Send update request if updateMask has paths
    if updateMask != nil && len(updateMask.Paths) > 0 {
        req := &pb.Update<Kind>Request{
            <Kind>:     desired,    // GCP reads new label values from desired.Labels
            UpdateMask: updateMask, // contains "labels" if metadata.labels changed
        }
        ...
    }
    ...
}
```

## 3. Common Pitfalls to Avoid
- **Do not use deprecated helpers** like `label.NewGCPLabelsFromK8sLabels` or manual map copying. Always use the canonical `label.GCPLabels(u)`.
- **Do not forget to test.** Ensure E2E `update.yaml` test fixtures include additions, modifications, or removals of `metadata.labels` to prevent label reconciliation bugs from slipping past CI.
