# Skill: Record Real GCP Logs

This skill provides a structured workflow for running end-to-end tests against real GCP APIs to generate and record authentic golden HTTP logs (`_http.log`).

## Critical Rules

*   **Never Fake or Manually Edit Golden yamls or HTTP Logs**: You are strictly forbidden from using text-editing tools (like `replace`, `write_file`, or `sed`) to create or modify `.golden.yaml` and `_http.log` files. Golden logs MUST be generated by executing `hack/record-gcp` against live GCP APIs.
*   **Run find-test-targets Before Committing**: Always run `go run ./hack/find-test-targets` before committing code/manifest updates (or before pushing to the PR branch) to ensure all working tree changes and local modifications are analyzed for affected test fixtures.
*   **Provide Timestamps in PDT**: When starting and finishing running `hack/record-gcp`, capture and provide the exact timestamps in PDT in your summary comment so reviewers can cross-verify against GCP server logs.
*   **Record All Affected Test Fixtures**: Never record only a subset of affected fixtures. Ensure all test folder names identified for the affected Kinds are executed and recorded.
*   **Handling record-gcp Failures**: If `record-gcp` fails, the bot should attempt to debug and fix the test case configuration (e.g., resolving IP address range conflicts, API/service enablement, or configuration schema issues). If it still fails after 3 distinct retry attempts, the bot must halt, escalate the failure to the human reviewer, and clearly explain the blocker/error in a comment.

## Workflow

### Step 0: Remove from Ratcheting Exclusions (MANDATORY)

Before running the test cases against real GCP, you **MUST** ensure the target resource is removed from the ratcheting exclusion list in `tests/e2e/ratcheting.go`. This enables Server-Side Apply (SSA) creation and re-reconciliation testing, which is a fundamental use case KCC resources must support.

1. Open `tests/e2e/ratcheting.go`.
2. Locate the function `ShouldTestRereconiliation`.
3. Locate the `switch` statement that checks `primaryResource.GroupVersionKind()`.
4. If there is a `case` block for your target resource's `GroupKind`, remove that `case` line from the switch statement.

---

### Step 1: Discover Test Targets

Run `hack/find-test-targets` **before committing the changes since the last push** (while working tree modifications or branch commits are present):

```bash
go run ./hack/find-test-targets
```

The tool inspects uncommitted working tree changes (staged and unstaged) against `HEAD` as well as untracked files, outputting a map of affected Kinds, whether the whole kind is affected (`all: true`), and the test case folder names:

```yaml
ComputeRouterNAT:
  all: true
  tests:
    - computerouternat
    - computerouternat-direct
    - computerouternatbasic-direct
StorageBucket:
  all: false
  tests:
    - storagebucketbasic
```

> **Tip**: If your changes are already committed on your branch, pass `--base` to diff against your base branch or commit (e.g. `go run ./hack/find-test-targets --base=master`).

---

### Step 2: Execute Real GCP Recording

#### 1. Fast vs. Slow Execution Strategy
*   **Fast resources (<10 min per test)**:
    - **If `all: true` (Whole-Kind change)**: You can record all tests for the Kind in a single command:
      ```bash
      hack/record-gcp "fixtures/<kind_lowercase>"
      ```
    - **If `all: false` (Selective manifest / reference change)**: Run only the affected test case(s):
      ```bash
      hack/record-gcp "fixtures/^<testname>$"
      ```

*   **Slow resources (>10 min per test)** (e.g. `ContainerCluster`, `ContainerNodePool`, `SQLInstance`, `ComposerEnvironment`):
    Run individual test fixtures in parallel using unique `ARTIFACTS` directories (regardless of `all`):
    ```bash
    ARTIFACTS="$(mktemp -d)" hack/record-gcp "fixtures/^<testname>$"
    ```

#### 2. Special Scenarios
> **Note**: Across all recording scenarios, `hack/record-gcp` supports targeting either an individual test fixture (`"fixtures/^<testname>$"`) or all fixtures of a Kind (`"fixtures/<kind_lowercase>"`).

*   **Greenfield Audit Probing**: If working on a greenfield resource with audit logging probes:
    ```bash
    RECORD_AUDIT_PROBE=1 hack/record-gcp "fixtures/^<testname>$"
    # Or for all fixtures of the kind:
    RECORD_AUDIT_PROBE=1 hack/record-gcp "fixtures/<kind_lowercase>"
    ```
*   **Migration from Terraform to Direct**:
    Always execute in sequence:
    ```bash
    # 1. Base test run
    hack/record-gcp "fixtures/^<testname>$"  # or: hack/record-gcp "fixtures/<kind_lowercase>"

    # 2. Migration in-place validation
    RUN_TESTS="TestMigrationToDirect/fixtures/^<testname>$" hack/record-gcp  # or: RUN_TESTS="TestMigrationToDirect/fixtures/<kind_lowercase>" hack/record-gcp
    ```

#### 3. Troubleshooting API / Permissions Issues
*   If an API service is disabled, enable it:
    ```bash
    gcloud services enable <service>.googleapis.com
    ```
*   If `hack/record-gcp` fails due to test manifest configuration issues (e.g. IP range conflict or schema typo), fix the configuration and retry. If it still fails after 3 distinct retry attempts, pause and summarize the blocker for the human reviewer.

---

### Step 3: Verify Test Completion (Mandatory)

Do NOT rely solely on top-level exit codes or `git status`. Verify that each test completed its full lifecycle by checking stdout for:
1. `=== RUN   TestAllInSeries/fixtures/<testname>` (confirms subtest matched and started).
2. Resource reached `Ready` (`status.condition.status: True`) for create (and update, if present).
3. Deletion completed (`Done waiting for resource to delete`).
4. `wrote updated golden output to .../_http.log` was logged (and file exists on disk).
5. No fatal panics, timeouts, or permission aborts.
