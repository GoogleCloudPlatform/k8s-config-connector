When implementing VertexAIFeaturestoreEntityType, I found:
1. `VertexAIFeaturestoreEntityType` is a child resource under `VertexAIFeaturestore`, with canonical GCP URL: `projects/{project}/locations/{location}/featurestores/{featurestore}/entityTypes/{entityType}`.
2. In KRM, its parent is specified via `spec.featurestore` (in the format `projects/{project}/locations/{location}/featurestores/{featurestore}`) rather than having separate `projectRef` or `location` fields.
3. We parse `spec.featurestore` using an internal `featurestoreParentFormat` `gcpurls.Template`, which cleanly handles both plain resource paths (`projects/...`) and fully-qualified URLs (`https://aiplatform.googleapis.com/...`). To prevent naming conflicts with `FeaturestoreParent` (which already exists in `vertexaifeaturestore_identity.go` representing a project+location parent), we named the template struct `entityTypeParentFeaturestore`.
4. Its status does not contain `externalRef` or `name`, so per SKILL.md, no status cross-check was implemented in `GetIdentity`, and no schema changes were made.
5. In `Normalize`, since it is a legacy Terraform-managed resource without `status.externalRef`, we use `refs.NormalizeWithFallback`, checking that the `Ready` condition is `True` before building the external string via `getIdentityFromVertexAIFeaturestoreEntityTypeSpec`.
6. Running `WRITE_GOLDEN_OUTPUT=1 go test -v ./pkg/cli/powertools/cais/...` updated the golden `_identities.yaml` for `vertexaifeaturestoreentitytypefeature-basic`, changing `VertexAIFeaturestoreEntityType` CAIS URL from `unknown` to `//aiplatform.googleapis.com/projects/${projectId}/locations/us-central1/featurestores/featurestore${uniqueId}/entityTypes/entitytype${uniqueId}`.
7. Both the full resource URL and parent featurestore URLs are present in `docs/ai/metadata/discovery_names.jsonl` and `cloudassetinventory_names.jsonl`, allowing `TestRegisteredTemplatesMatchCAI` to pass without adding exceptions to `pkg/gcpurls/registry_test.go`.
